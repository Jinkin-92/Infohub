# 订阅源辅助登录与统一管理方案

创建时间：2026-04-03
状态：Draft

## 1. 目标

本方案解决两个问题：

1. 为所有需要登录态的平台提供统一的“辅助登录”能力，不再让用户分别理解 Cookie、Token、DevTools、远程调试等技术细节。
2. 将当前分散的“添加源”“设置”“标签”能力收敛为一个统一的订阅源管理中心，支持管理每个订阅源的卡片信息、栏目、类别和删除。

本轮方案默认保留当前技术边界：

- RSSHub 仍然是知乎、微博、X、部分平台的抓取出口。
- 微信保留现有专用采集链路，并把现有微信登录能力整合进统一设置页。
- 不强求所有平台在第一阶段都支持全自动登录，但统一抽象必须先建立。

## 2. 推荐方案

推荐采用“双层统一”方案：

1. 登录层统一：引入 `PlatformAuthManager` 概念，每个平台都声明自己的认证方式、状态机、所需凭证、自动采集能力和校验方法。
2. 管理层统一：新增“订阅源中心”，每个订阅源都拥有统一元数据卡片，平台差异通过扩展字段展示，而不是拆散到不同页签。

推荐理由：

- 保留现有实现投资，不推翻微信链路。
- 可以把微博二维码/手机号辅助登录、微信二维码登录、未来 X/知乎 登录都纳入同一套框架。
- 用户心智会从“我在配环境变量”转成“我在连接一个平台账号并管理订阅源”。

## 3. 辅助登录统一方案

### 3.1 核心抽象

后端新增统一认证注册表：

- `platform_auth_sessions`
- `PlatformAuthProvider`
- `PlatformCredentialStore`

每个平台 provider 至少实现以下能力：

- `getCapabilities()`
- `startLogin()`
- `getSessionStatus()`
- `cancelLogin()`
- `validateCredentials()`
- `persistCredentials()`
- `describeCredentialHealth()`

统一状态机：

- `idle`
- `launching`
- `awaiting_user_action`
- `verifying`
- `ready`
- `expired`
- `failed`
- `cancelled`

### 3.2 平台分层

按平台能力分三类：

1. 原生二维码/网页登录平台
   - 微信公众号
   - 微博
   - 未来可扩展到小红书
2. 外部 Cookie 注入平台
   - RSSHub 依赖的知乎、X 等
3. 无需登录平台
   - 新闻 RSS
   - 自定义 RSS
   - YouTube 原生 RSS
   - B 站公开抓取

### 3.3 设置页信息架构

当前设置页拆为两层：

1. `平台连接`
   - 显示所有平台卡片
   - 每张卡片展示：平台名称、认证方式、当前状态、最近校验时间、失效提醒
   - CTA：连接、重新登录、校验、断开
2. `抓取配置`
   - 仍保留 RSSHub 环境变量等高级配置
   - 仅给高级用户展开

推荐平台卡片字段：

- 平台名称
- 平台图标和颜色
- 认证方式
- 当前状态
- 最近成功校验时间
- 依赖的订阅源数量
- 主按钮
- 次按钮

### 3.4 微信方案整合

微信保留现有两条能力，但并入统一平台卡片：

1. 二维码登录
2. 手动填 Cookie + Token

微信卡片的主流程建议为：

- 默认主按钮：`二维码登录`
- 辅助入口：`手动填写凭证`
- 状态区：显示 Cookie、Token、采集配置、最近采集结果

原单独的 `WeChatTab` 不再作为独立页签，而是变成“微信平台详情抽屉”。

### 3.5 微博方案

微博采用独立浏览器会话辅助登录，不再依赖复用现有 DevTools 会话。

推荐流程：

1. 用户点击“连接微博”
2. 系统启动独立 Chrome Profile
3. 用户在该窗口中扫码或手机号登录
4. 后端轮询 Cookie
5. 检测到 `SUB` / `SUBP` 后自动写入 `WEIBO_COOKIES`
6. 系统自动执行一次微博凭证校验
7. 连接成功后允许直接创建微博订阅源

微博卡片额外展示：

- 当前 Cookie 预览
- 目标验证 URL
- 最近一次校验结果
- 快速按钮：`添加微博源`

### 3.6 统一 API

新增统一认证路由：

- `GET /api/auth/platforms`
- `GET /api/auth/:platform/status`
- `POST /api/auth/:platform/start`
- `GET /api/auth/:platform/sessions/:sessionId`
- `POST /api/auth/:platform/sessions/:sessionId/cancel`
- `POST /api/auth/:platform/verify`
- `DELETE /api/auth/:platform/credentials`

保留兼容层：

- `/api/wechat/*`
- `/api/cookie/*`

但前端新界面只走统一认证 API。

## 4. 订阅源统一管理方案

### 4.1 目标形态

当前“设置里的 sources 列表”过于偏运维，缺少内容管理信息。建议升级为真正的“订阅源中心”。

每个订阅源都是一张标准卡片，分三层信息：

1. 基础身份
   - 名称
   - 平台
   - 头像或封面
   - 原始 URL
   - 平台唯一标识
2. 内容归属
   - 栏目
   - 类别
   - 标签
3. 运行状态
   - 启用/停用
   - 最近抓取时间
   - 最新内容时间
   - 错误数
   - 最后错误

### 4.2 信息模型

建议在现有 `sources` 表基础上扩展：

- `card_title`
- `card_subtitle`
- `cover_url`
- `description`
- `column_id`
- `category_id`
- `sort_order`
- `pinned`
- `auth_platform`
- `auth_required`
- `auth_status_cache`

新增两张管理表：

- `source_columns`
- `source_categories`

推荐关系：

- 一个订阅源属于一个栏目
- 一个订阅源属于一个类别
- 一个订阅源可继续拥有多个标签

栏目和类别的职责区分：

- 栏目：偏展示分区
  - 例如：核心关注、日更、深度、快讯
- 类别：偏主题分类
  - 例如：AI、财经、科技、宏观

标签继续承担灵活筛选职责：

- 例如：创业、Agent、OpenAI、投研

### 4.3 前端结构

推荐将当前设置页中的 `sources` 升级为两段式界面：

1. 顶部筛选栏
   - 搜索
   - 平台筛选
   - 栏目筛选
   - 类别筛选
   - 状态筛选
2. 卡片网格或列表
   - 默认卡片视图
   - 支持切换紧凑列表视图

每张订阅源卡片操作：

- 启用/停用
- 编辑信息
- 手动抓取
- 查看认证状态
- 移动栏目
- 更改类别
- 删除

点击卡片进入详情抽屉：

- 平台信息
- 认证信息
- 最近内容预览
- 抓取历史
- 错误日志
- 编辑表单

### 4.4 编辑能力

订阅源编辑表单建议统一支持：

- 卡片标题
- 副标题
- 描述
- 栏目
- 类别
- 标签
- 封面图
- 抓取频率
- 是否启用

平台扩展字段在详情里分组展示：

- 微信：fakeid、采集模式、全文抓取
- 微博：uid、认证状态、目标验证 URL
- 知乎：用户 id、Cookie 状态

### 4.5 删除策略

删除采用两段式策略：

1. 软删除订阅源
   - 订阅源从主列表移除
   - 内容默认保留
2. 二次危险操作
   - 可选择是否联动删除历史 items

删除弹窗必须明确展示：

- 将删除哪个订阅源
- 是否保留历史内容
- 是否断开该平台登录

## 5. 推荐交互流

### 5.1 连接平台后直接建源

目标是把“登录”和“添加订阅源”串成一个完整任务。

示例：微博

1. 用户在“平台连接”里点连接微博
2. 登录成功
3. 系统显示“已连接微博”
4. 弹出快速添加框：
   - 粘贴微博主页
   - 或从最近访问目标自动回填
5. 自动创建源并跳转到订阅源卡片详情

示例：微信

1. 用户在微信卡片里完成二维码登录
2. 系统显示“已连接微信公众号后台”
3. 用户可直接搜索公众号并创建订阅源

### 5.2 添加订阅源流程重构

`AddSourceModal` 改成三段式：

1. 输入链接
2. 平台检测
3. 认证检查

如果平台需要认证但未连接：

- 不再静默失败
- 直接提示：
  - 该平台需要先连接账号
  - 提供“去连接”按钮

### 5.3 订阅源中心中的栏目和类别

推荐默认预置：

栏目：

- 核心关注
- 高频更新
- 深度阅读
- 观察中

类别：

- AI
- 科技
- 财经
- 商业
- 宏观
- 其他

这样用户第一次进入管理中心就有可落位的结构，不需要先配置才能开始。

## 6. 实施分期

### Phase 1：统一登录入口

目标：先把用户心智统一。

- 新增 `平台连接` 区域
- 微博辅助登录接入统一平台卡片
- 微信现有登录方案并入设置页
- 保留原高级 Cookie/RSSHub 配置，但折叠到高级区域

### Phase 2：订阅源卡片化管理

目标：让每个订阅源可编辑、可归类、可管理。

- 扩展 `sources` 元数据
- 新增栏目/类别表
- 把设置页中的 sources 列表升级为卡片管理中心

### Phase 3：登录与建源打通

目标：从“连接平台”一步走到“添加源”。

- 连接成功后自动推荐创建源
- 认证缺失时 AddSourceModal 能跳转到对应平台连接
- 卡片详情可查看平台认证状态

### Phase 4：内容侧联动

目标：栏目和类别真正进入内容浏览主链路。

- 首页 Feed 支持按栏目和类别筛选
- 源卡片编辑的栏目/类别反向影响内容视图

## 8. 最小验收标准

- 设置页可以看到统一的平台连接区域。
- 微信原有登录方案可以在设置页统一入口下使用。
- 微博可通过辅助登录自动写入 Cookie。
- 订阅源中心支持查看所有订阅源卡片。
- 每张卡片支持编辑栏目、类别、标题和删除。
- 添加订阅源时，如果平台需要认证而未认证，界面会明确提示并可跳转连接。

## 9. 推荐下一步

如果进入实施，推荐先做这 3 个故事：

1. 统一平台连接模型和设置页平台卡片
2. 订阅源数据模型扩展：栏目、类别、卡片元数据
3. 订阅源中心 UI：卡片列表 + 详情抽屉 + 删除流

这三步完成后，整个系统的“连接平台 → 创建源 → 管理源 → 读取内容”主路径会第一次真正闭环。
