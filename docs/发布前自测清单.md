# 发布前自测清单

这份清单的目标不是“证明绝对没 bug”，而是尽量在你自己的电脑上把最常见的发布问题提前暴露出来。

## 1. 先跑自动化冒烟测试

先从用户实际入口启动应用：

```powershell
.\start.bat
```

快速检查：

```powershell
node .\scripts\run-local-smoke.mjs
```

深度检查：

```powershell
node .\scripts\run-local-smoke.mjs --deep
```

全链路自测：

```powershell
node .\scripts\run-full-selftest.mjs
```

如果你希望它自动补安装并重新拉起本地服务：

```powershell
node .\scripts\run-full-selftest.mjs --install --start
```

如果你想固定检查某一个源，可以指定源 id：

```powershell
node .\scripts\run-local-smoke.mjs --deep --source-id 35
```

`quick` 模式会检查：
- 前端首页是否可访问
- 后端 `/health` 是否正常
- 平台状态接口是否可读
- 订阅源列表接口是否可读

`deep` 模式会额外检查：
- 微信已连接时，`/api/auth/wechat/verify` 是否返回有效
- 微信、微博这些核心登录链路是否可用
- 其他已连接平台的测试结果会显示为通过或警告
- 一条指定或自动选择的启用源是否能手动采集

`run-full-selftest.mjs` 会串起来检查：
- 后端回归测试
- 本地 deep smoke
- 前端 E2E 页面流
- 添加订阅源
- 设置页打开与切换
- 平台连接面板渲染
- 订阅源手动刷新
- 公开订阅源入口

## 2. 手动回归关键链路

每次准备给别人测试或推广前，至少手动走一遍下面这些流程：

- 首次启动后首页能正常打开，没有白屏
- 可以新增一个公开订阅源
- 刷新后内容列表能看到新增内容
- 关闭应用再重启，原有配置仍然存在
- 微信重新连接后，连接状态显示正常
- 微博重新连接后，测试连接成功
- 点击某条源“手动采集”时不会再出现明显报错
- 收藏、已读、筛选这些日常功能还能正常用

## 3. 稳定性检查

在真正给别人用之前，建议至少做一次 30 到 60 分钟的稳定性观察：

- 保持应用运行
- 每隔 10 到 15 分钟刷新一次
- 看日志里是否反复出现同一种错误
- 确认没有越跑越慢
- 确认没有残留大量浏览器进程

重点关注这些信号：

- 反复出现 `503`、`invalid session`、`timed out`
- 前端能打开，但 API 开始失败
- 重连成功后立刻又显示失效
- 某个源一刷新就卡很久

## 4. Windows 环境专项检查

因为当前推荐发布形态是 Windows 本地运行，这几项很值得专门测一下：

- 用 `start.bat` 能成功启动
- 电脑重启后第一次启动仍然正常
- 端口 3000 或 3002 被占用时，错误信息是否容易理解
- 本机没有登录 Chrome 的情况下，基础功能是否仍可启动
- 更新后重新运行 `update.bat` 不会把环境搞坏

## 5. 什么时候不该继续推广

如果出现下面任一情况，建议先别发给别人：

- `node .\scripts\run-local-smoke.mjs --deep` 跑不通
- 微信或微博重连后状态不稳定
- 同一个操作连续两三次结果不一致
- 重启后配置丢失
- 手动采集经常失败且没有明确原因

## 6. 推荐发布节奏

比较稳的节奏是：

1. 本地修复
2. 跑 `quick` 冒烟
3. 手动回归关键链路
4. 跑 `deep` 冒烟
5. 保持运行观察一段时间
6. 再发给朋友或开始推广

这样虽然不等于正式 QA，但已经能挡掉一大批“别人一上手就坏”的问题。
